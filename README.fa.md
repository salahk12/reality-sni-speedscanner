# اسکنر سرعت SNI برای Reality

**فارسی** · **[English](README.md)**

پیدا کردن SNI هایی که از داخل شبکه‌ی سانسورشده هنوز **آپلود سریعی** دارند — نه صرفاً آن‌هایی که وصل می‌شوند.

> فورکی از [AminDaProgrammer/Master_Reality_SNI_Scanner](https://github.com/AminDaProgrammer/Master_Reality_SNI_Scanner)
> که معماری سرور/کلاینتش پایه‌ی این کار است. README اصلی در
> [README-upstream.md](README-upstream.md) نگه داشته شده.

---

## چرا

SNI فقط در هندشیک TLS جابه‌جا می‌شود، پس وسوسه‌انگیز است که فکر کنیم همه‌ی SNI ها یک‌جور عمل می‌کنند. این‌طور نیست. شکل‌دهنده‌های ترافیک روی SNI کار می‌کنند و اولین چیزی که خفه می‌کنند مسیر **آپلود** است: یک SNI می‌تواند سرعت دانلود کاملش را حفظ کند در حالی که آپلودش به قطره‌چکان افتاده. پینگ این را نشان نمی‌دهد. باید بایت واقعی جابه‌جا کرد.

دو SNI روی یک سرور، یک پورت و یک پروتکل، با چند دقیقه فاصله، می‌توانند یک مرتبه‌ی بزرگی در آپلود اختلاف داشته باشند. این ابزار مشخص می‌کند کدام‌ها **امروز و روی خط خودِ شما** هنوز خوب‌اند.

---

## چطور کار می‌کند

سرور به ازای هر SNI یک اینباند Reality جداگانه می‌سازد. کلاینت از داخل هر کدام یک تونل باز می‌کند و می‌سنجد چقدر سریع می‌تواند آپلود کند. پروب‌ها موازی اجرا می‌شوند و به یک آپلودکننده‌ی سریال خوراک می‌دهند، پس هیچ‌وقت دو اندازه‌گیری سر پهنای‌باند شما رقابت نمی‌کنند، ولی نتایج از همان ثانیه‌های اول شروع به آمدن می‌کنند.

<div dir="ltr">

```
   کامپیوتر شما                                  سرور خارج (مثلاً آلمان)
   ┌───────────────────────┐                  ┌──────────────────────────┐
   │ client-speedScanner   │──── API ────────▶│ server-sniScanner        │
   │                       │                  │  یک اینباند Reality      │
   │  probe  ──┐           │                  │  به ازای هر SNI، با      │
   │           ├─ tunnel ──┼─────────────────▶│  پورت و target خودش      │
   │  upload ──┘           │                  └──────────────────────────┘
   └───────────────────────┘                              │
              │                                           ▼
              └──────── سنجش Mbps ──────────────▶ speed.cloudflare.com
```

## شروع سریع

### ۱. روی سرور خارج

<div dir="ltr">

```bash
git clone https://github.com/salahk12/reality-sni-speedscanner.git
cd reality-sni-speedscanner
sudo bash install-server.sh
```

</div>

این اسکریپت Xray-core و وابستگی‌های پایتون را نصب می‌کند، بازه‌ی پورت اینباندها را رزرو می‌کند، فایروال را باز می‌کند و API را به‌صورت سرویس systemd بالا می‌آورد تا با ریبوت هم برگردد. در پایان آدرس سرور و دستور دقیق کلاینت را چاپ می‌کند.

> **از یک VPS تمیز استفاده کنید.** اسکنر کانفیگ Xray را بازنویسی و سرویس را ری‌استارت می‌کند. روی سروری که x-ui، 3x-ui، مرزبان یا هیدیفای دارد این کار با پنل تداخل می‌کند — نصب‌کننده روی چنین سروری اجرا نمی‌شود مگر `--force` بدهید.

اگر پورت‌های پیش‌فرض با چیزی تداخل داشتند:

<div dir="ltr">

```bash
sudo bash install-server.sh --api-port 9090 --base-port 40000 --count 500
```

</div>

### ۲. روی کامپیوتر خودتان

نیاز دارید به پایتون ۳، فایل `xray` (یا `xray.exe` کنار اسکریپت) و PySocks:

<div dir="ltr">

```bash
pip install requests PySocks
```

</div>

قبل از اسکن مطمئن شوید سرور در دسترس است:

<div dir="ltr">

```bash
curl http://<SERVER_IP>:8080/health      # باید {"status": "ok", ...} بدهد
```

</div>

بعد اسکن کنید:

<div dir="ltr">

```bash
python client-speedScanner.py --server <SERVER_IP> --api-port 8080 \
    --sni-file sni-1000.txt --limit 300 --workers 16 --upload-seconds 5
```

</div>

خروجی‌ها در پوشه‌ی `results/` ساخته می‌شوند: یک گزارش `.html` مرتب‌شونده، به‌همراه `.csv`، `.json`، `.txt` و فایل `_links.txt` که در هر خطش یک `vless://` آماده‌ی import دارد.

## لیست‌های SNI

سه لیست همراه مخزن است. هر دامنه **از یک سرور خارج** تست شده که سه شرط لازم برای dest ِ Reality را دارد: هندشیک TLS 1.3، مذاکره‌ی HTTP/2، و گواهی معتبر برای همان نام.

| فایل | محتوا |
| --- | --- |
| `sni-1000.txt` | ۱۰۰۰ دامنه‌ی خارجی از ۷۶۴ سازمان |
| `sni-1000-v2.txt` | ۱۰۰۰ تای دیگر، بدون هیچ هم‌پوشانی با اولی |
| `sni-1000-ir.txt` | ۱۰۰۰ دامنه‌ی داخلی ایرانی |

لیست‌های خارجی **زیرساخت‌محور** مرتب شده‌اند: اندپوینت‌های `api.`، `cdn.`، `edge.`، `dl.` و `static.` قبل از صفحه‌های اصلی. دامنه‌ی صفحه‌اصلیِ برندهای معروف اولین نامی است که شکل‌دهنده‌ی ترافیک یاد می‌گیرد و به همین دلیل زودتر از بقیه آپلودشان خفه می‌شود، در حالی که اندپوینت‌های تله‌متری و آپدیت همان شرکت‌ها سالم می‌مانند. در ۳۰۰ ردیف اول اصلاً هیچ `www.` وجود ندارد، پس `--limit 300` فقط اندپوینت‌های ساکت را به شما می‌دهد.

لیست ایرانی برعکس مرتب شده — سایت‌های بزرگ و شناخته‌شده اول — چون هدف یک SNI داخلی این است که **شبیه ترافیک عادی داخلی** به نظر برسد، و برای این کار یک سایت معروف بهتر از یک اندپوینت گمنام است.

**لیست ایرانی ذاتاً ناپایدار است.** در تست پشت‌سرهم، هشت SNI خارجی در چهار اجرای متوالی ۸/۸ دادند در حالی که هشت SNI ایرانی ۳/۸، ۷/۸، ۵/۸ و ۶/۸ دادند. هیچ چیزی در خود SNI ها عوض نشده بود — رسیدن به هاست‌های ایرانی از بیرون صرفاً کم‌اعتمادتر است. اسکن داخلی را چند بار بزنید و آن‌هایی را نگه دارید که مکرراً قبول می‌شوند.

### ساخت لیست اختصاصی خودتان

<div dir="ltr">

python3 tools/build_sni_candidates.py > candidates.txt
python3 tools/validate_sni.py candidates.txt --json report.json > verified.txt
python3 tools/rank_sni.py report.json --limit 1000 --pin your.known.good.host

## اسکن هم‌زمان از چند سیستم

برای مقایسه‌ی SNI ها بین ISP های مختلف باید کلاینت را از چند خط اجرا کنید. این کار شدنی است، ولی نه با اجرای ساده‌ی دوباره‌ی کلاینت.

سرور **یک** کانفیگ Xray دارد و روی هر تغییر آن را ری‌استارت می‌کند، پس کلاینت دومی که کانفیگ خودش را اعمال کند اینباندهای کلاینت اول را جایگزین می‌کند و انتقال‌هایش را وسط کار قطع می‌کند. اندازه‌گیری با سه کلاینت روی یک سرور:

<div dir="ltr">

```
بدون --use-existing   client1:  0/40   client2: 38/40   client3: 39/40
با    --use-existing   client1: 39/40   client2: 34/40   client3: 40/40
```

</div>

پس یک بار اینباندها را منتشر کنید و بعد همه‌ی سیستم‌ها از همان استفاده کنند:

<div dir="ltr">

```bash
# یک بار، از هر سیستمی
python client-speedScanner.py --server <IP> --api-port 8080 \
    --sni-file sni-1000.txt --batch-size 1000 --skip-speed

# بعد روی هر سیستم، هم‌زمان
python client-speedScanner.py --server <IP> --api-port 8080 \
    --sni-file sni-1000.txt --use-existing --workers 16 --upload-seconds 5
```

</div>

فلگ `--use-existing` نقشه‌ی زنده‌ی SNI به پورت را می‌خواند و هیچ چیزی اعمال نمی‌کند، پس هیچ کلاینتی مزاحم دیگری نمی‌شود. همه‌ی سیستم‌ها دقیقاً یک مجموعه اینباند روی یک سرور را تست می‌کنند و همین نتایج را قابل مقایسه می‌کند.

۱۰۰۰ اینباند حدود ۵۵۰ مگابایت رم روی سرور می‌گیرد. اگر حافظه کم است، به‌جایش ۳۰۰ تا ۵۰۰ تا منتشر کنید.

## گزینه‌ها

| فلگ | کار |
| --- | --- |
| `--sni-file FILE` | لیستی که اسکن می‌شود، هر خط یک دامنه |
| `--limit N` | فقط N ردیف اول فایل. لیست‌ها از قبل رتبه‌بندی شده‌اند، پس این یعنی N تای بهتر |
| `--workers N` | تعداد پروب موازی (پیش‌فرض ۸). آپلود همیشه سریال است، پس این عدد مرحله‌ی آپلود را کوتاه نمی‌کند |
| `--upload-seconds N` | بودجه‌ی زمانی هر اندازه‌گیری آپلود (پیش‌فرض ۱۰) |
| `--upload-mb N` | سقف حجم نمونه برای هر SNI (پیش‌فرض ۱۶). اگر آپلودتان بالای ~۱۳ مگابیت است و اعداد نوسان دارند، بالاتر ببرید |
| `--probe-timeout N` | مهلت اتصال تونل به ثانیه (پیش‌فرض ۵). روی خط کند بالاتر ببرید |
| `--use-existing` | اسکن روی کانفیگی که از قبل روی سرور زنده است. برای اجرای هم‌زمان چند کلاینت لازم است |
| `--skip-speed` | فقط دسترس‌پذیری و پینگ، بدون انتقال داده |
| `--with-download` | سنجش دانلود هم انجام شود (پیش‌فرض خاموش) |
| `--top N` | فقط N تای سریع‌تر تست آپلود شوند. پیش‌فرض ۰ یعنی همه |
| `--phased` | اول همه پروب، بعد همه آپلود. پینگ و jitter تمیزتر، ولی نتیجه‌ی اول دیرتر |
| `--probe-gate` | حذف SNI وقتی پروبش شکست بخورد، به‌جای تست آپلود گرفتن از آن |
| `--transport` | tcp، websocket، grpc، http2، xhttp، quic، splithttp |
| `--shuffle` | به‌هم‌ریختن ترتیب فایل (رتبه‌بندی از پیش‌آماده را بی‌اثر می‌کند) |

### خواندن امتیاز

<div dir="ltr">

```
پیش‌فرض           score = 0.75 x upload + 0.25 x latency
--phased          score = 0.65 x upload + 0.25 x latency + 0.10 x jitter
--with-download   وزن آپلود به 0.45 می‌رسد و دانلود 0.20 می‌گیرد
```

</div>

هر جمله نسبت به بهترین مقدار **در همان اجرا** نرمال می‌شود، پس امتیازها فقط داخل یک اسکن معنی دارند و بین دو اسکن قابل مقایسه نیستند.

## رفع اشکال

**`curl .../health` جواب refused می‌دهد** — سرویس اجرا نشده. `systemctl status sniscanner` و `tail -40 /var/log/sniscanner.log` را ببینید.

**`curl .../health` تایم‌اوت می‌شود** — پورت فیلتر است. هم در فایروال VPS و هم در فایروال بیرونیِ ارائه‌دهنده بازش کنید. بازه‌ی اینباندها (پیش‌فرض `30000-31000`) هم باید باز شود، نه فقط پورت API.

**همه چیز در مرحله‌ی اول شکست می‌خورد** — معمولاً یعنی بازه‌ی پورت اینباندها از سیستم شما در دسترس نیست. یکی را مستقیم تست کنید: `curl -v telnet://<IP>:30000`.

**API روی پورتی غیر از آنچه خواستید بالا آمده** — سرور وقتی پورت درخواستی اشغال باشد به پورت آزاد بعدی می‌رود. پورتی که واقعاً گرفته، هنگام شروع و در `/var/log/sniscanner.log` چاپ می‌شود.

**همه‌ی SNI ها مرده به نظر می‌رسند** — به احتمال زیاد PySocks نصب نیست. `requests` بدون آن هیچ پراکسی SOCKS باز نمی‌کند و خطایش دقیقاً شبیه تونل خراب است.

**عدد آپلود یک SNI بین اجراها نوسان زیادی دارد** — آپلود شما آن‌قدر سریع است که سقف `--upload-mb 16` قبل از `--upload-seconds` تمام می‌شود و کل اندازه‌گیری داخل TCP slow start می‌افتد. `--upload-mb` را بالا ببرید.

**SNI ای که می‌دانید کار می‌کند، شکست‌خورده گزارش می‌شود** — پروب یک درخواست HTTP به `speed.cloudflare.com` **از داخل تونل** است، نه پینگ به خود SNI، پس روی خط کند ممکن است تایم‌اوت شود در حالی که تونل سالم است. این حکم نهایی نیست: آن SNI همچنان تست آپلود می‌شود و آپلود تصمیم می‌گیرد. اگر زیاد تکرار شد `--probe-timeout` را بالا ببرید.

## چه چیزی در این فورک عوض شد

نسخه‌ی اصلی می‌گوید کدام SNI وصل می‌شود. هرچه در ادامه می‌آید حاصل تلاش برای اینکه بگوید کدام هنوز **سریع** است — به‌همراه اندازه‌گیری‌ای که هر باگ را لو داد.

**سنجش آپلود.** همان قابلیتی که نبود. حجم هر نمونه از روی یک اجرای کالیبراسیون کوتاه تعیین می‌شود تا نزدیک بودجه‌ی زمانی تمام شود، به‌جای حجم ثابتی که روی خط سریع در یک چشم‌به‌هم‌زدن تمام می‌شود و روی خط کند دقیقه‌ها معطل می‌کند.

**یک اینباند برای هر SNI، هرکدام با target خودش.** نسخه‌ی اصلی یک batch کامل را در یک اینباند می‌گذاشت که target اش **اولین** SNI ِ همان batch بود. این هم false negative می‌سازد — با `target = www.cloudflare.com`، تست `dl.google.com` چهار بار از چهار بار شکست می‌خورد و به‌محض هم‌خوان شدن target بلافاصله کار می‌کند — و هم false positive، چون دامنه‌ای که اصلاً resolve نمی‌شود «سالم» گزارش می‌شود صرفاً به این دلیل که در همان لیست `serverNames` است که خودتان تازه ساخته‌اید. بعد همان دامنه‌ی جعلی رتبه‌ی اول می‌شود، target ِ مرحله‌ی بعد می‌شود و کل اجرا را ساقط می‌کند.

**اسکن موازی که واقعاً موازی است.** نسخه‌ی اصلی پورت SOCKS کلاینت را برای همه‌ی ورکرها روی ۱۰۸۰ ثابت کرده بود **و** در ابتدای هر ورکر `kill_all_xray()` صدا می‌زد، پس با پیش‌فرض پنج ورکر هرکدام چهارتای دیگر را می‌کشت و بعد سر یک پورت دعوا می‌کردند.

**تایم‌اوت‌هایی که واقعاً عمل می‌کنند.** `requests` عدد اسکالر `timeout` را هم به فاز اتصال می‌دهد هم به خواندن، پس تونل مرده کل آن مقدار را می‌سوزاند. بدتر اینکه بدنه‌ی آپلود یک generator بود که `requests` را به chunked encoding می‌برد — و در آن مسیر urllib3 اصلاً تایم‌اوت را روی سوکت اعمال نمی‌کند. در تست با یک پراکسی که عمداً جواب نمی‌داد، بدنه‌ی دارای طول در ۵ ثانیه شکست خورد در حالی که همان درخواست با بدنه‌ی generator بعد از ۷۵ ثانیه هنوز آویزان بود. حالا یک SNI مرده حدود پنج ثانیه هزینه دارد، نه یک دقیقه.

**ری‌استارتی که از پس کانفیگ بزرگ برمی‌آید.** قبل از ری‌استارت Xray منتظر آزاد شدن واقعی پورت‌ها می‌ماند، وضعیت failed ِ systemd را پاک می‌کند (پنج شکست پیاپی، سرویس را کاملاً از استارت شدن باز می‌دارد) و پورت‌هایی را که پروسه‌ی دیگری گرفته رد می‌کند — قبلاً یک پورت اشغال وسط بازه، کل کانفیگ هزار اینباندی را از کار می‌انداخت.

**کشتنی که فقط پروسه‌ی خودمان را می‌گیرد.** `pkill -9 xray` زیررشته‌ای مطابقت می‌دهد، پس `xray-linux-amd64` ِ یک پنل x-ui را هم می‌کشد و روی هر اعمال کانفیگ، مشتری‌های آن پنل را قطع می‌کند. حالا هر دو طرف فقط پروسه‌هایی را می‌کشند که خودشان ساخته‌اند.

**محافظ‌های سرور.** برای گرفتن یک پورت، سرویس شناخته‌شده را نمی‌کشد — نسخه‌ی اصلی برای تصاحب پورت ۴۴۳ دستور `lsof -ti:443 | kill -9` می‌زد که روی یک وب‌سرور یعنی کشتن nginx یا LiteSpeed — و اگر پنل پراکسی از قبل در حال اجرا باشد اصلاً بالا نمی‌آید.

**اصلاحات کوچک‌تر.** استفاده از `socks5h` تا DNS داخل تونل حل شود نه با resolver ِ سانسورشده؛ نام‌های درست transport در لینک (`ws` و `h2`) تا لینک‌های تولیدشده واقعاً import شوند؛ دور انداختن یک نمونه‌ی warm-up قبل از سنجش پینگ، که بدون آن هندشیک سرد سرور به‌صورت ۷۵ میلی‌ثانیه jitter دیده می‌شد روی خطی که jitter واقعی‌اش زیر ۱۰ بود؛ و اضافه شدن PySocks به نصب‌کننده.

# اسکنر سرعت SNI برای Reality

**فارسی** · **[English](README.md)**

SNI هایی را پیدا می‌کند که از داخل شبکه‌ی سانسورشده هنوز **آپلود سریعی** دارند — نه صرفاً آن‌هایی که وصل می‌شوند.

شکل‌دهنده‌های ترافیک روی SNI کار می‌کنند و اولین چیزی که خفه می‌کنند آپلود است: یک SNI می‌تواند دانلود کاملش را حفظ کند در حالی که آپلودش فروریخته. پینگ این را نشان نمی‌دهد، پس این ابزار بایت واقعی جابه‌جا می‌کند. دو SNI روی یک سرور و یک پورت می‌توانند ده برابر در آپلود اختلاف داشته باشند.

فورکی از [Master_Reality_SNI_Scanner](https://github.com/AminDaProgrammer/Master_Reality_SNI_Scanner) — فهرست تغییرات و دلیلشان در [CHANGELOG.md](CHANGELOG.md).

## نصب سرور (VPS خارج)

<div dir="ltr">

```bash
curl -fsSL https://raw.githubusercontent.com/salahk12/reality-sni-speedscanner/main/install-server.sh | sudo bash
```

</div>

Xray-core و وابستگی‌ها را نصب می‌کند، بازه‌ی پورت اینباندها را رزرو می‌کند، فایروال را باز می‌کند و API را به‌صورت سرویس systemd بالا می‌آورد. در پایان دستور کلاینت را چاپ می‌کند.

برای دادن گزینه از داخل پایپ به `-s --` نیاز است:

<div dir="ltr">

```bash
curl -fsSL .../install-server.sh | sudo bash -s -- --api-port 9090 --count 500
```

</div>

| گزینه | |
| --- | --- |
| `--api-port N` | پورت API (پیش‌فرض ۸۰۸۰) |
| `--base-port N` | اولین پورت اینباند (پیش‌فرض ۳۰۰۰۰) |
| `--count N` | تعداد پورت اینباند (پیش‌فرض ۱۰۰۰) |
| `--force` | اجرا روی سروری که پنل پراکسی دارد |

> **از VPS تمیز استفاده کنید.** اسکنر کانفیگ Xray را بازنویسی و سرویس را ری‌استارت می‌کند و این با پنل x-ui / 3x-ui / مرزبان / هیدیفای روی همان سرور تداخل دارد. نصب‌کننده بدون `--force` اجرا نمی‌شود.

## اجرای اسکن (کامپیوتر خودتان)

نیاز به پایتون ۳، فایل `xray` (یا `xray.exe` کنار اسکریپت)، `requests` و `PySocks`:

<div dir="ltr">

```bash
pip install requests PySocks
# اوبونتو ۲۴ / دبیان ۱۲ (PEP 668): sudo apt install python3-requests python3-socks
```

</div>

<div dir="ltr">

```bash
curl http://<SERVER_IP>:8080/health      # باید {"status": "ok", ...} بدهد

python client-speedScanner.py --server <SERVER_IP> --api-port 8080 \
    --sni-file sni-1000.txt --limit 300 --workers 16 --upload-seconds 5
```

</div>

خروجی در `results/` ساخته می‌شود: گزارش `.html` مرتب‌شونده به‌همراه `.csv`، `.json`، `.txt` و `_links.txt` که هر خطش یک `vless://` آماده‌ی import است.

## لیست‌های SNI

هر دامنه **از یک سرور خارج** تست شده که سه شرط لازم برای dest ِ Reality را دارد: TLS 1.3، مذاکره‌ی HTTP/2، و گواهی معتبر برای همان نام.

| فایل | |
| --- | --- |
| `sni-1000.txt` | ۱۰۰۰ دامنه‌ی خارجی از ۷۶۴ سازمان |
| `sni-1000-v2.txt` | ۱۰۰۰ تای دیگر، بدون هم‌پوشانی با اولی |
| `sni-1000-ir.txt` | ۱۰۰۰ دامنه‌ی داخلی ایرانی |

لیست‌های خارجی **زیرساخت‌محور** مرتب شده‌اند (`api.`، `cdn.`، `edge.`، `dl.`، `static.` قبل از صفحه‌های اصلی)، چون صفحه‌اصلیِ یک برند اولین نامی است که شکل‌دهنده یاد می‌گیرد در حالی که اندپوینت‌های تله‌متری همان شرکت سالم می‌مانند. در ۳۰۰ ردیف اول هیچ `www.` وجود ندارد، پس `--limit 300` فقط اندپوینت‌های ساکت را می‌دهد.

لیست ایرانی برعکس مرتب شده — سایت‌های بزرگ و شناخته‌شده اول — چون یک SNI داخلی باید شبیه ترافیک عادی داخلی به نظر برسد. **انتظار ناپایداری داشته باشید:** هشت SNI خارجی در چهار اجرای متوالی ۸/۸ دادند، در حالی که هشت تای ایرانی ۳/۸، ۷/۸، ۵/۸ و ۶/۸ دادند. اسکن داخلی را چند بار بزنید و آن‌هایی را نگه دارید که مکرراً قبول می‌شوند.

ساخت لیست اختصاصی (اعتبارسنج را **روی همان سروری که اینباندها را میزبانی می‌کند** اجرا کنید):

<div dir="ltr">

```bash
python3 tools/build_sni_candidates.py > candidates.txt
python3 tools/validate_sni.py candidates.txt --json report.json > verified.txt
python3 tools/rank_sni.py report.json --limit 1000 --pin your.known.good.host
```

</div>

## اسکن از چند سیستم

سرور یک کانفیگ Xray دارد و روی هر تغییر ری‌استارتش می‌کند، پس کلاینت دومی که کانفیگ خودش را اعمال کند اینباندهای اولی را پاک می‌کند. سه کلاینت هم‌زمان:

<div dir="ltr">

```
بدون --use-existing   0/40   38/40   39/40
با    --use-existing  39/40   34/40   40/40
```

</div>

یک بار اینباندها را منتشر کنید و بعد همه‌جا از همان استفاده کنید:

<div dir="ltr">

```bash
# یک بار، از هر سیستمی
python client-speedScanner.py --server <IP> --api-port 8080 \
    --sni-file sni-1000.txt --batch-size 1000 --skip-speed

# بعد روی هر سیستم، هم‌زمان
python client-speedScanner.py --server <IP> --api-port 8080 \
    --sni-file sni-1000.txt --use-existing --workers 16 --upload-seconds 5
```

</div>

۱۰۰۰ اینباند حدود ۵۵۰ مگابایت رم می‌گیرد؛ اگر حافظه کم است ۳۰۰ تا ۵۰۰ تا منتشر کنید.

## گزینه‌ها

| فلگ | |
| --- | --- |
| `--sni-file FILE` | لیست اسکن، هر خط یک دامنه |
| `--limit N` | N ردیف اول فایل. لیست‌ها از قبل رتبه‌بندی شده‌اند، پس یعنی N تای بهتر |
| `--workers N` | پروب موازی (پیش‌فرض ۸). آپلود سریال است، پس این آن را کوتاه نمی‌کند |
| `--upload-seconds N` | بودجه‌ی زمانی هر آپلود (پیش‌فرض ۱۰) |
| `--upload-mb N` | سقف حجم نمونه (پیش‌فرض ۱۶). اگر آپلودتان بالای ۱۳ مگابیت است و اعداد نوسان دارند بالاتر ببرید |
| `--probe-timeout N` | مهلت اتصال تونل (پیش‌فرض ۵). روی خط کند بالاتر ببرید |
| `--use-existing` | اسکن روی کانفیگ زنده‌ی سرور بدون اعمال چیزی. برای چند کلاینت هم‌زمان لازم است |
| `--skip-speed` | فقط دسترس‌پذیری و پینگ |
| `--with-download` | سنجش دانلود هم انجام شود (پیش‌فرض خاموش) |
| `--phased` | اول همه پروب، بعد همه آپلود. پینگ و jitter تمیزتر، نتیجه‌ی اول دیرتر |
| `--probe-gate` | حذف SNI وقتی پروبش شکست بخورد، به‌جای تست آپلود گرفتن |
| `--top N` | فقط N تای سریع‌تر. پیش‌فرض ۰ یعنی همه |
| `--transport` | tcp، websocket، grpc، http2، xhttp، quic، splithttp |

امتیاز به‌صورت پیش‌فرض `0.75 × upload + 0.25 × latency` است. نسبت به بهترین مقدار **در همان اجرا** نرمال می‌شود، پس فقط داخل یک اسکن معنی دارد و بین دو اسکن قابل مقایسه نیست.

## رفع اشکال

| نشانه | علت |
| --- | --- |
| `/health` با refused | سرویس بالا نیست. `systemctl status sniscanner` و `tail /var/log/sniscanner.log` |
| `/health` تایم‌اوت | پورت فیلتر است. هم در فایروال VPS و هم فایروال ارائه‌دهنده بازش کنید — بازه‌ی اینباندها هم، نه فقط پورت API |
| همه چیز در مرحله‌ی اول شکست می‌خورد | بازه‌ی اینباندها در دسترس نیست. یکی را تست کنید: `curl -v telnet://<IP>:30000` |
| API روی پورتی غیر از انتظار | سرور به پورت آزاد بعدی می‌رود؛ در شروع و در لاگ چاپ می‌شود |
| همه‌ی SNI ها مرده به نظر می‌رسند | PySocks نصب نیست — `requests` بدون آن پراکسی SOCKS باز نمی‌کند |
| عدد آپلود بین اجراها نوسان دارد | آپلودتان آن‌قدر سریع است که `--upload-mb` نمونه را داخل TCP slow start تمام می‌کند. بالاتر ببرید |
| SNI سالمی شکست‌خورده گزارش می‌شود | پروب یک درخواست HTTP **از داخل تونل** است نه پینگ، پس روی خط کند تایم‌اوت می‌شود. این حکم نهایی نیست — آن SNI همچنان تست آپلود می‌شود. `--probe-timeout` را بالا ببرید |
